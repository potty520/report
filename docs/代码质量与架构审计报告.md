# 严重（S）—— 直接导致维护失控或线上踩坑

## S1. 全局异常处理器形同虚设：121 处 catch 把异常语义抹平为 `code=500`

**证据**
- `GlobalExceptionHandler.java:20-56` 已完整实现：`AccessDeniedException → HTTP 403`、`DuplicateKeyException → "数据已存在"`、`RuntimeException → 脱敏`、`Exception → "系统异常"`。
- 但 Controller 层另有 **121 处** `catch (RuntimeException e) { return Result.error(e.getMessage()); }`，并且前置 **78 处** `catch (AccessDeniedException e) { throw e; }` 纯转发样板。
- 分布（Top）：`TemplateController` 14、`AuditController` 11、`TaskController` 11、`FillController` 8、`RoleController` 7、`FileController` 6、`DatasourceController` 6。
- `Result.error(String)` 固定 `code=500`（`Result.java:32-34`），于是**参数错误、业务规则拒绝、数据库约束冲突在 HTTP 层全部是 200 + code 500**，前端无法区分。
- 更糟：`AuthController:96`、`UserController:47`、`FillController:190` 等处在 catch 里写 `Result.error("文件上传失败: " + e.getMessage())`，**绕过了 `Result.sanitizeMessage()` 的脱敏**（该脱敏就是为了拦 SQL/驱动原文）。

**影响**
- 维护性：新增接口必须复制 2~3 个 catch 块，漏一个行为就不一致；`Result.java` 注释里自称"119 处"，已与实际 121 处漂移。
- 可观测性：Service 抛出的异常被 Controller 吃掉，**日志里没有任何 error 记录**（全库仅 5 条 `log.error`），线上排障只能靠猜。
- 前端：`request.ts` 只能按 `code !== 200` 统一弹错，无法区分"要重新登录 / 无权限 / 表单校验失败"。

**改进**
1. **删掉所有 Controller 的 try/catch**，只保留 Service 抛出业务异常，由 `GlobalExceptionHandler` 统一出口（这个类本来就写好了，只是被架空了）。
2. 引入业务异常类型（当前 0 个）：

```java
public class BizException extends RuntimeException {
    private final int code;            // 4001 业务校验 / 4003 无权限 / 4040 不存在
    public BizException(int code, String msg) { super(msg); this.code = code; }
    public int getCode() { return code; }
}
```
```java
@ExceptionHandler(BizException.class)
public ResponseEntity<Result<?>> handleBiz(BizException e) {
    log.warn("业务异常 code={} msg={}", e.getCode(), e.getMessage());   // 补日志
    HttpStatus status = e.getCode() >= 4003 ? HttpStatus.FORBIDDEN
                       : e.getCode() == 4040 ? HttpStatus.NOT_FOUND : HttpStatus.BAD_REQUEST;
    return ResponseEntity.status(status).body(Result.error(e.getCode(), e.getMessage()));
}
```
3. `Result.error(String)` 保留，但把 `sanitizeMessage` 作为**唯一**出口，禁止在 catch 里手工拼 `e.getMessage()`。

**收益预估**：124 个文件可净删约 **900~1,100 行**（121×2 行 catch + 78 行转发），Controller 平均缩短 20%。

## S3. `useGeneratedKeys` 假设与 mapper 语义混乱：`RptTaskAssignMapper.selectByTaskId` 返回带 join 的"半个视图"

**证据**
- `RptTaskAssignMapper.java:11`
  ```java
  @Select("SELECT a.*, d.dept_name FROM rpt_task_assign a LEFT JOIN sys_dept d ON a.dept_id = d.id WHERE a.task_id = #{taskId}")
  List<RptTaskAssign> selectByTaskId(Long taskId);
  ```
- `RptTaskAssign` 实体里**没有** `deptName` 字段（`model/RptTaskAssign.java` 只有 id/taskId/deptId/userId/assignType/status/createTime），`a.*` 与 join 出来的列会被 MyBatis 静默丢弃。
- 同一功能在 `RptTaskService.getAssigns()` 用 `Wrappers.lambdaQuery()` 另写了一遍（**重复 DAO 方法**）。
- 全库 **21 个 Mapper 中 17 个是空的 `BaseMapper` 壳**（`{}`），真正 SQL 反而写在 `jdbcTemplate` 里（87 处），形成"MPS 与裸 JDBC 混用"。

**影响**
- 死代码 + 误导：新人会以为有 `deptName` 可用。
- `jdbcTemplate.queryForList(...)` 返回 `Map<String,Object>`，**字段名不受编译期保护**，改列名只能靠 grep。

**改进**
```java
// 1) 要么给实体补 @TableField(exist = false) private String deptName;
// 2) 要么删掉这个方法，Service 统一走 lambdaQuery
public List<RptTaskAssign> getAssigns(Long taskId, String assignType) {
    return rptTaskAssignMapper.selectList(Wrappers.<RptTaskAssign>lambdaQuery()
            .eq(RptTaskAssign::getTaskId, taskId)
            .eq(StrUtil.isNotBlank(assignType), RptTaskAssign::getAssignType, assignType));
}
```
- 把 `ReportStatsService.baseSql()` 的 6 段长 SQL（`ReportStatsService.java:180-235`，单方法 54 行）迁到 `resources/mapper/ReportStatsMapper.xml`，与"**Mapper XML 与注解混用**"的现状统一为 XML 风格。

## S4. `Result.error` 只有 500，`Result` 里 `msg` 字段与前端契约名不一致

**证据**
- 后端：`Result` 含 `{code, msg, data}`（`Result.java:12-15`）。
- 前端：`api.ts:6-10` `ApiResponse<T> = { code, data, msg }` —— 一致。
- 但 197 处 `Result.error(...)` 里 **196 处默认 500**，仅 1 处显式 403（`Result.java:39` 的 `error(int,String)`）。`unauthorized()/forbidden()` 两个工厂方法**从未被调用**（死代码）。
- 全部 Controller 返回 `Result<?>`（HTTP 200），**只有** `GlobalExceptionHandler` 的 `AccessDeniedException` 分支和 `JwtAuthFilter` 返回真实 4xx。前端 `request.ts` 的重试/跳登录逻辑因此只对极少数路径生效。

**影响**：错误码退化成一个值，可观测性与协议表达力都损失。

**改进**：定义错误码枚举（见 M6），`Result.error(ErrorCode)` 重载；Controller 返回 `Result` 的同时由 `ResponseEntity` 携带真实 HTTP 状态（业务校验 400 / 无权限 403 / 不存在 404 / 冲突 409 / 系统 500）。

## S5. 全部 61 处 `@Transactional` 都没有 `rollbackFor`，且 0 处 `readOnly`

**证据**
- `@Transactional` 61 处，`rollbackFor` 出现 **0 次**，`readOnly=true` **0 次**。
- Spring 默认仅对 `RuntimeException`/`Error` 回滚。本项目大量方法签名声明 `throws SQLException`／内部 `catch (SQLException e) { throw new RuntimeException(...) }`（`MaterializeService:112/129/157/246`），目前**靠包装成 RuntimeException 侥幸回滚**。一旦有人改成受检异常或 `throw new IOException`，事务将静默不回滚。
- 典型高风险：`RptTaskDataService.importExcel`（100 行，含 3 次跨表写入 + 目标库写入）、`commitToTarget`（78 行）、`RptTaskService.generatePeriodicTasks`（86 行，N 次 insert）。

**改进**
```java
@Transactional(rollbackFor = Exception.class)
public Map<String, Object> importExcel(...) { ... }

@Transactional(readOnly = true)   // 查询类：getFillList / getAuditList / trajectory / correctList / rates / view
```
- 建议加一条 Code Review 检查项：**Service 写方法必须 `rollbackFor = Exception.class`**。

- 后果①：**前端可以把 `createTime`、`auditStatus`、`inboundStatus` 等内部字段直接写进来**（如 `POST /task` 不校验 `task.setStatus(0)`，但 `PUT /task` 的 `toTaskPayload` 会带 `status`，后端 `updateById` 全字段覆盖）。
- 后果②：实体里混着 `@TableField(exist = false)` 的展示字段（`RptTask`:39-53 共 7 个、`RptTaskData`:44-64 共 10 个、`RptTemplate`:34-42 共 6 个）→ **实体同时是 DB 行、DTO、VO**，三个角色互相污染。
- 后果③：Controller 里干组装（`AuthController:45-100` 54 行拼 userInfo、`CompatController:127-165` 循环拼 3 个 join），Service 返回值是 `Map<String,Object>`（`RptTaskDataService.commitToTarget`/`importExcel`、`ReportStatsService.view`）→ **编译期零类型安全**。

**改进**
- 新增 `dto/` 包 + `MapStruct`（或手写 `XxxConverter`），`@RequestBody` 一律用 DTO。
- 实体只保留 DB 列；展示字段迁 VO。
- `Map<String,Object>` 返回值改为泛型的 `IngestResult`、`LedgerViewPage` 等 record/POJO。

## M9. 参数与请求绑定方式**全项目不统一**（`@RequestParam` vs `@RequestBody` 混用）

**证据**
- 同一模块内既用 query 又用 body：`TemplateController` 的 `deploy(id, @RequestParam datasourceId, tableName)` 与 `add(@RequestBody RptTemplate)`；`OnlineUserController` 全 query；`StatisticsRuleController.save(@RequestBody)`。

- 参数校验缺失：`@RequestParam Integer status` 未限值（如 `TaskController.toggleStatus` 可传 99），`DatasourceController:106` 把 `port` 声明成 `String` 再 `Integer.parseInt`（`NumberFormatException` 直接冒到用户）。

**改进**：统一 REST 风格——查询用 query（`@ModelAttribute PageQuery`），命令用 `@RequestBody` + `@Valid`；`port` 用 `Integer` + `@Min/@Max`。

## M10. 建表/迁移策略重复且分散

**证据**
