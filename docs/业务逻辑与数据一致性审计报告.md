## 0. 先纠正几个前提认知

### 0.1 RptTask.status 是 5 态，不是 4 态

| 值 | 含义 | 依据 |
|---|---|---|
| 0 | 草稿 | `docs/database.sql:215`、`RptTaskService.java:54` |
| 1 | 已发布 | `RptTaskService.java:68` |
| 2 | 填报中 | `RptTaskService.java:123` |
| 3 | 已完成 | `ReportStatsService.java:272`、`OverviewController.java:151` |
| 4 | 已关闭 | `TaskController.java:138` |

**但没有任何代码路径能把任务置成 3**：唯一写入口 `updateStatus(taskId, status)`（`RptTaskService.java:258`）只有两处调用——发布传 1、关闭传 4。`case 3` 分支（267-281）是**死代码**。

后果：首页 `completedTasks`、`chart?type=status` 的"已完成"恒为 0，`/overview/dashboard` 的 `fillRate = completed/(filling+completed)` **恒等于 0**。

### 0.2 审核字段是"两套并存且互相打架"

项目同时维护：
- 单级：`rpt_task_data.audit_status`（0 待审 / 1 通过 / 2 驳回）
- 两级：`dept_audit_status` + `task_audit_status`
- 另有"最终结论"复用了 `audit_status`

| 方法 | 写 deptAudit | 写 taskAudit | 写 auditStatus | 行号 |
|---|---|---|---|---|
| `audit()`（旧单级） | ✗ | ✗ | ✓ = 传参 | 195-240 |
| `deptAudit()` | ✓ | ✗ | 仅驳回时 =2 | 640-662 |
| `taskAudit()` | 只读校验 | ✓ | ✓ | 666-693 |

**实际后果**：
1. 走"部门审核→任务方审核"链路的已通过数据，在部门审核通过到任务方审核之间 `audit_status` 仍是 0 → **会一直挂在"待审"列表里**。
2. 走 `/audit/approve` 的数据 `deptAuditStatus` 永远是 0 → **永远无法进入任务方审核**。
3. `RptTaskDataService.java:235-239` 把任务级 `auditStatus` 置 1 —— 而该字段是 `@TableField(exist=false)`（`RptTask.java:55`），**这段代码是空操作**。

### 0.3 F06「fillData 幂等」**不成立**

```java
RptTaskData existData = rptTaskDataMapper.selectOne(...task_id, fill_user_id);
if (existData != null) { updateById } else { insert }
```

典型 check-then-act，**且 `rpt_task_data` 上没有 `(task_id, fill_user_id)` 唯一约束**。并发请求（双击保存、前端重试、导入与手填同时）都会 select 到 null 然后都 insert → 重复数据。之后所有 `selectOne` 调用在 MySQL 上抛 `TooManyResultsException`，该用户该任务从此**无法保存、提交、审核**。

### 0.4 孤儿任务的成因（已在生产验证）

`RptTemplateService.deleteById()`（264-269）：

```java
public void deleteById(Long id) {
    rptTemplateMapper.deleteById(id);          // 物理删除
    rptTemplateFieldMapper.delete(...);        // 只顺手删字段
}
```

**完全没有检查 rpt_task / rpt_task_data / rpt_template_auth 是否引用该模板**，无软删除，无外键。这就是"删模板 → 任务变孤儿"的直接成因。

## 2. 事务与并发

### 2.1 @Transactional 与自调用

全库 61 处 `@Transactional`。**逐条检查结论**：
- 全部标注在 public 方法、且是 `@Service` 类的 public 方法 ✓
- **同类自调用只有 2 处**，都不丢事务：
  - `assignTaskByDepts()` → `assignTask()`：外层已有事务

- **`SysUserService.assignRoles` 等 4 个方法缺 `@Transactional`**：`assignRoles` 先 delete 再逐条 insert，中途失败留下"角色被清空"中间态 | `SysUserService.java:172-176` | 中

### 2.4 周期任务生成幂等性 —— 严重

`RptTaskService.generatePeriodicTasks()`（352-438）三重缺陷：
1. **check-then-insert 无唯一约束**：`rpt_task` 无 `(parent_task_id, belong_time, dept_id)` 唯一键
2. **判重粒度错误**：判重条件 `(parent_task_id, belong_time)`，插入却按部门循环
3. **定时任务无分布式互斥**：`@EnableScheduling` 裸开，无 ShedLock/Redis/DB 锁。**多实例部署时每个实例每天各执行一遍**

后果：每期每部门重复生成子任务 → "我的任务"出现 N 条同名、台账重复。

### 2.5 乐观锁/悲观锁全部缺失

全库 grep：**无 `@Version`、无 `FOR UPDATE`、无 `OptimisticLockerInnerInterceptor`、无 Redisson**。`MyBatisPlusConfig.java:12-16` 只注册了分页插件。

### 4.4 台账统计口径（重要，直接导致考核失真）

`rates()`（133-175）四指标：

| 指标 | 分子 | 分母 | 问题 |
|---|---|---|---|

## 9. 整体健壮性评级

| 维度 | 评级 | 说明 |
|---|---|---|
| 安全与鉴权 | **B-** | 角色体系完整，但大量"有角色无数据归属"的越权读接口，多处 fail-open |
| 状态机完整性 | **C** | 主链路能跑通，但"已完成"是死状态，assign 可复活任务，模板侧无状态机 |
| 并发与事务 | **D+** | 无任何锁/版本号/唯一约束；关键操作全是 check-then-act；定时任务多实例必重复 |
| 数据一致性 | **D** | 删除无引用保护（已产生线上孤儿）、软硬删混用、外键全缺、关键唯一键全缺 |
| 业务规则 | **C** | 截止校验只覆盖一半入口；台账口径（部门归属）错误；数据申请与权限脱钩 |
| 异常处理 | **C-** | 约 60 处 Controller 吞异常 + 脱敏叠加，可观测性差 |

**综合评级：C-（勉强可内测，不适合生产）**

主要扣分集中在**数据一致性（D）与并发（D+）**。这两块不修，任何一次双击、任何一次多实例滚动发布、任何一次误删模板，都会产生不可自动恢复的数据污染——这正是线上 55 条孤儿任务的成因。

**上线前最低门槛**：Top 5 + 第二批 6-13 项。其中 **1/2/3 三项涉及唯一键/外键，必须在上线前完成存量数据清理后再执行 DDL**：先确认无重复数据，清理后再加约束，否则 DDL 会直接失败。
