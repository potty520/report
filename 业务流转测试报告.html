三、V01「审核 25 秒超时」—— 问题不存在

结论：原报告的 25,139ms 超时在生产环境无法复现，且技术上不可能。

补正发起（T12）48 ms

三方交叉验证

  • 接口实测：完整走了「提交→部门审核→任务方审核」真实链路，每步 85ms 左右
  • 数据量核查：rpt_task_data 1 行、rpt_task_assign 51 行、rpt_task 55 行
  • 索引核查：task_id/dept_id/fill_user_id 索引均已存在

在 1 行数据的表上，SQL 不可能耗时 25 秒。

可能原因（建议后续核实）

原报告的 code=-1 msg=TimeoutError('timed out') 是 Python requests 客户端抛出的超时，不是服务端返回的业务错误码。可能原因：
  • 测试脚本设置了极短的超时时间，而当时服务刚启动或正在 GC
  • 测试环境（192.168.1.41）与本次生产环境（103.85.25.169）配置不同
  • 当时服务端存在其他阻塞（首次 JIT 编译、连接池初始化）
建议：若后续再出现，用 jstack 抓线程栈定位，而不是继续加索引。

四、本次新发现的缺陷

高

前后端任务字段不匹配 —— 前端新建任务必然失败

现象在「任务管理 → 任务制定」页面填写完整表单点「确定」，返回 操作失败：数据校验不通过或数据库约束冲突，任务未被创建
根因前端 TaskFormParams 提交 {name, year, period, startDate, endDate, status, description}；后端实体 RptTask 实际字段为 {taskName, templateId, belongTime, fillDeadline, fillingCycle}。两套字段名几乎完全不同，后端拿不到必填的 taskName 与 fillingCycle
影响页面上新建任务 100% 失败，只能通过 API 创建
实测证据用前端真实 payload 提交 → code=500，回查 createdCount=0
修复方向① 前端改为提交后端字段名（推荐）；② 或后端加 DTO + @JsonProperty 映射。并补充前后端字段契约测试
中

任务列表缺少操作入口

现象「任务制定」列表页每行只有「删除」按钮
缺失编辑、发布、分派、关闭 四个关键操作在列表中均无入口
影响用户无法在界面上推进任务流转（发布/分派/关闭），业务闭环在 UI 层断裂
实测证据页面按钮集合 = [搜索, 重置, 新增任务, 删除]，无 编辑/发布/分派
修复方向列表操作列补齐：编辑、发布（仅草稿可见）、分派、关闭（仅已发布可见）
中

LocalDateTime 反序列化不支持标准格式

现象POST /task 传 "fillDeadline": "2026-12-31 23:59:59" → Text could not be parsed at index 10
根因未注册 JavaTimeModule 反序列化器，也未加 @JsonFormat；spring.jackson.date-format 只对 java.util.Date 生效
现状只有 ISO 格式（2026-12-31T23:59:59）能解析
影响当前前端不传 fillDeadline，暂无实际触发；一旦修复上一条让前端传日期，必然踩坑
修复方向配置 spring.jackson.serialization.write-dates-as-timestamps: false，或全局注册 JavaTimeModule 指定 yyyy-MM-dd HH:mm:ss
设计

新建模板默认不可用（非缺陷）

现象通过 API 新建模板后 status=0（停用）且 audit_status=0（待审），立即建任务报「模板未启用」
性质设计如此 —— RptTemplateService.add 明确 setStatus(0) // 草稿
提示使用 API/脚本创建模板时，必须先执行「启用 + 审核通过」两步才能使用
