二、核心改动：check-then-act → 条件 UPDATE

问题：原来所有状态流转都是「先 SELECT 判断，再 UPDATE 写入」。两次操作之间有窗口期， 两个并发请求都读到「待审」，就都会执行更新——后写的覆盖先写的，审核结果的「谁审的、什么结论」会错乱。
// 修复前（有并发窗口）
if (data.getStatus() != 1) throw ...;　　// 读
data.setAuditStatus(1);
mapper.updateById(data);　　　　　　　　// 写（覆盖他人结果）

// 修复后（原子抢占）
int claimed = mapper.update(null, Wrappers.<RptTaskData>lambdaUpdate()
　　.set(RptTaskData::getAuditStatus, 1)
　　.eq(RptTaskData::getId, dataId)
　　.eq(RptTaskData::getStatus, 1)　　　　　// 前置条件进 WHERE
　　.and(w -> w.isNull(...).or().eq(..., 0)));
if (claimed == 0) throw new RuntimeException("状态已变更，请刷新后重试");
覆盖范围：提交填报、审核通过/驳回、部门审核、任务方审核、任务发布、任务关闭、保存草稿共 7 个流转点。

三、定时任务互斥（不引入新依赖）

原实现 @EnableScheduling 裸跑，多实例部署时每个实例每天各执行一遍，配合 check-then-insert 会重复生成子任务。
// 数据库唯一键抢占，无需 ShedLock
DELETE FROM rpt_schedule_lock WHERE job_name=? AND locked_at < NOW()-INTERVAL 30 MINUTE;
INSERT INTO rpt_schedule_lock (job_name, instance, locked_at) VALUES (?,?,NOW());
// 抛 DuplicateKeyException 即说明其他实例正在执行 → 直接跳过
// finally { DELETE ... } 释放；崩溃残留由 30 分钟超时清理
另外把「超期扫描」从周期生成里拆出来独立加锁——原来生成失败会把超期提醒一起跳过。
